# Accessibility (A11y) Audit & Standards

Accessibility is a design and implementation goal for this project. The checks below describe implemented behavior; they are not a formal WCAG conformance claim. Validate releases with automated checks, keyboard-only use, and assistive technology.

## Standards Followed

- **Keyboard Navigation:** Native controls use native keyboard behavior; MultiSelect, Combobox, MenuButton, TreeView, CommandPalette, Tabs, and Modal include custom keyboard handling.
- **Focus Management:** 
  - Modals trap keyboard focus and restore focus to the element that opened them.
  - The accessible form example moves focus to its error summary after invalid submission; summary links target the corresponding fields.
  - MenuButton returns focus to its trigger after an action or Escape; SkipLink targets the page's main landmark.
  - CommandPalette returns focus to its trigger after a command or dismissal. Multi-step navigation moves focus to the new step heading.
- **ARIA Roles & Attributes:**
  - `role="dialog"` and `aria-modal="true"` for modals.
  - `role="combobox"` and `aria-expanded` for MultiSelects.
  - `aria-invalid` and `aria-describedby` for error states on inputs.
  - Form fields associate visible labels, hints, and errors with their controls; required state is conveyed with native `required`.
  - Combobox exposes its active suggestion and labelled listbox; menu actions expose menuitem semantics.
  - Inline alerts and live regions use polite status or assertive alert semantics according to urgency.
  - Breadcrumbs expose a named navigation landmark and current-page state; Stepper communicates current/completed steps; TreeView exposes hierarchy and roving focus.
  - LanguageSwitcher provides a labelled native select or a menu-button variant with checked menuitemradio states; both return BCP 47 locale tags to the consuming application.
  - Content patterns use semantic headings, articles, lists, time elements, and named navigation landmarks. Decorative icon content is hidden from assistive technology when its meaning is already conveyed by text.
  - Images require alternative text (empty text is supported for decorative images); video players support caption tracks and transcript links, and audio players support transcripts.
  - CAPTCHA is only an accessible wrapper around a real provider challenge. Provider accessibility and server-side token verification remain the integrator’s responsibility; a visual checkbox is not treated as verification.
  - Login fields use visible labels, required semantics, password-manager autocomplete, an announced visibility toggle state, and generic submission errors; the consuming application must provide secure authentication and transport.
- **Color Contrast:** Colors target WCAG 2.1 AA contrast; a complete contrast audit remains outstanding.
- **Screen Reader Support:** Use of semantic HTML and appropriate ARIA labels to ensure meaningful content for assistive technologies.
